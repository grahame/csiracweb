# player.cvt, and what is known about it

`player.cvt` is T746, the program that played tunes on CSIRAC's loudspeaker.
Its tape is headed `Lucy Long 1 18 September, 1998. T746 B208`, which dates it
to the reconstruction of the CSIRAC music rather than to the machine's working
life.

It reads its tune from a 12-hole data tape. **That tape's format has not been
worked out**, and no tune tape is bundled. This is a record of what two
attempts did establish, so that a third does not start from nothing.

## How the program is laid out

Reading the tape in stores 507 words, `0 0` to `15 26`, and stops at `0 13`
(`PS T`) leaving the sequence register at `0 14`. Execution then goes

```
 0 14   A SA     clear the accumulator
 0 15   K  S     jump, by way of K, to 0 25
 0 25   S  D     the sequence register into D15
 0 26   I  C     read a row from the tape into C
```

Two routines matter.

**The note decoder, `0 26` to `1 10`.** It reads a row, tests it, and works out
a timing from it. The arithmetic is real: `K XB` and `RB XB` multiply, `HU PK`
builds an address in K so that the `M C` and `M PA` after it are indexed, and
it leaves by `D S`. A note is therefore not a small integer that indexes a
table; it is a value the program computes with.

**The tone loop, `9 17` to `9 19`.**

```
 9 17   C  P     a word to the loudspeaker
 9 18   M PS     add a word from store to the sequence register
 9 19   M PS     and again
```

`M PS` is a computed relative jump, so the delay between one pulse and the next
is fetched from store. That is the whole of CSIRAC's pitch control: the tone
loop pulses, then jumps by however much the decoded note said.

## What the input register does to it

The `I` source gate hands over the value already in the input register and only
then reads the next row, so a program reads one row behind the tape. After
loading, the input register holds zero, so the first `I C` puts **zero** in C,
the test at `0 28` fails, and the program stops at `0 13` without playing a
note.

Priming the input register gets it running: with any non-zero value it decodes
169 notes from 900 rows and drives the speaker. So the reading and decoding
work. From the console the way to do that is the I register switches, `I` on
the operations menu, whose value is disjoined into every read.

## Where it stops being understood

- With small integer rows the tone loop settles at a constant spacing of 6 and
  22 commands whatever the rows contain, so the notes are being decoded to the
  same timing. That is a buzz, not a tune.
- With rows carrying an X punch, which is what a value large enough to be a
  useful fraction needs, the program produces no pulses at all: those take a
  different branch out of the decoder.
- Searching all 507 possible entry points for one that produces sustained
  notes found none, so the tune is not sitting in the loaded image waiting to
  be started.

The 164 words that decode as `C P` from `5 6` onwards look like tune data read
as instructions rather than a table the player walks, but that has not been
confirmed either.

## What to try next

Instrument the decoder rather than guessing at its input. Watch the word that
reaches the tone loop's delay at `9 18` for a given input row, build the map
from row to delay over the whole range of rows, and invert it. That gives the
encoding directly instead of by search. The scaffolding for this already
exists: `Machine.onStore` follows writes to store, and `onHoot` carries the
command count, which is what the tune tapes' tests already measure.

## The tunes that are bundled

`Hoot.cvt`, `Scale.cvt` and `Chime.cvt` do not use this player. They are
straight runs of commands generated by `tools/make-tunes.mjs`, punched for this
emulator rather than recovered from CSIRAC, and they are limited to about three
quarters of a second for the reasons the README gives.
